# concept-explainer — 概念学习资料生成 Skill

## 1. 设计意图（为什么要做这件事）

大多数人学一个新概念，会卡在三处：

1. **不知道"应该学到什么程度"才算懂**——没有学习目标 → 浅尝辄止。
2. **被动接收解释，没有主动提问**——读完就忘 → 没有核心问题驱动。
3. **学完无法检验自己**——没有自测 → 以为自己会了。

本 Skill 围绕这三个卡点设计：先立目标（知道终点在哪），再提核心问题（驱动思考），最后给自测（闭环验证）。中间三段（个人解释 / 结构化解释 / 应用案例 / 概念辨析）是"知识本体"，参考来源是"可核查锚点"。

## 2. 适用场景

加载本 Skill 的触发条件（任一）：

- 用户说"系统了解一下 X"、"用学习资料的方式给我讲 X"。
- 用户给出概念名并希望得到一份"可以拿给别人看"的资料。
- 用户想对一个已经知道的概念做结构化复盘。

不适用：

- 用户只要一句话答案（不要硬塞完整资料）。
- 主题是 API 用法、代码示例——交给代码类 Skill。
- 主题不是概念而是业务需求。

## 3. 输入信息

**必填**：

- `concept`：要学习的概念名（中英文皆可；缩写先展开全称）。

**可选**（不填则采用默认，并在产出末尾"参数"小节注明）：

- `level`：受众水平（`beginner` / `intermediate` / `advanced`），默认 `intermediate`。
- `prior_knowledge`：用户已掌握的先验，避免重复铺垫。
- `angle`：侧重角度（"工程实现" / "历史脉络" / "数学原理"），默认综合。
- `output_path`：HTML 输出路径，默认 `learning-materials/<concept-kebab-case>.html`。

## 4. 生成步骤（按顺序执行，缺一不可）

1. **概念锁定**：写出 `concept` 的最权威定义（英文全称、首次提出者或出处）。
2. **学习目标**：写 3–5 条"读完这份资料应该能……"的陈述句，覆盖"理解 / 应用 / 区分"三个层面。
3. **个人解释**：用第一人称、口语化、亲历者角度解释这个概念（"我把它理解为..."）。避免论文腔。
4. **核心问题**：围绕概念列 3–5 个关键问题，**问题本身要能驱动思考**（不是简单事实，而是"为什么会这样 / 跟谁有关 / 边界在哪"）。
5. **结构化解释**：拆解 2–5 个核心组件 / 步骤，给出最小但完整的工作流；能用伪代码、流程图或 ASCII 示意更好。
6. **应用案例**：一个真实可触达的案例（产品 / 系统 / 论文 demo / 工程实践），把概念"用起来"。
7. **概念辨析**：列 3–5 条最容易踩的坑、被滥用场景、与相邻概念的边界（如 Agent vs Chatbot）。
8. **自测问题**：3–5 道自测题，题型混合（理解类 + 应用类 + 辨析类），每题附"答案要点"。
9. **参考来源**：3–6 条可核查的真实链接，标注可信度（🟢 官方 / 🔵 学术 / 🟡 工程 / ⚪ 一般）。
10. **自检**：跑一遍第 7 节清单，全部通过再交付。
11. **写入文件**：渲染为单文件 HTML（结构见第 5 节），写到 `output_path`。

## 5. 输出结构（HTML 模板，顺序与锚点固定）

```
<article>
  <section id="goals">         <!-- 学习目标 -->
  <section id="personal">      <!-- 个人解释 -->
  <section id="core-questions"><!-- 核心问题 -->
  <section id="mechanism">     <!-- 结构化解释 / 核心机制 -->
  <section id="scenario">      <!-- 应用案例 -->
  <section id="contrast">      <!-- 概念辨析 -->
  <section id="quiz">          <!-- 自测问题 -->
  <section id="sources">       <!-- 参考来源 -->
  <footer id="meta">           <!-- 生成时间、Skill 版本、参数、人工核查记录 -->
</article>
```

CSS：浅色主题（IDE 为 light 时）、卡片化、最大宽度 880px、章节标题用蓝色下划虚线分隔。代码块用 `<pre><code>`，引用用 `<blockquote>`，自测题用 `<details>` 折叠。不依赖付费 CDN（Mermaid 例外，使用 jsdelivr 公开镜像）。

## 6. 参考来源硬约束

- **必须**真实、可点开的 URL，不得编造。
- **必须**至少 1 条官方文档或原始论文。
- 链接文字要让读者预判内容，不要写"链接1"、"参考1"。
- 每条链接后注明"可信度"：🟢 官方 / 🔵 学术 / 🟡 工程 / ⚪ 一般。
- 自检时若发现链接可疑，立即修正或删除，并在底部"核查记录"小节说明。

## 7. 自检清单（交付前必跑）

- [ ] 八个一级章节齐全且顺序正确（学习目标 / 个人解释 / 核心问题 / 结构化解释 / 应用案例 / 概念辨析 / 自测问题 / 参考来源）。
- [ ] "学习目标"3–5 条，覆盖理解 / 应用 / 区分三层面。
- [ ] "个人解释"是第一人称口语化，没有"本文将..."这种论文腔。
- [ ] "核心问题"至少 3 条，且都是"为什么 / 怎么 / 区别于什么"型而非事实查询型。
- [ ] "结构化解释"含至少 2 个组件或步骤，最好有伪代码或示意。
- [ ] "应用案例"是具体可触达的，不是"比如 AI 客服"这种泛指。
- [ ] "概念辨析"至少 3 条，每条用一句话说清边界。
- [ ] "自测问题"至少 3 题，每题有可折叠的"答案要点"。
- [ ] "参考来源"链接全部能点开，至少 1 条官方/学术来源。
- [ ] HTML 文件能直接在浏览器中打开（无未闭合标签、无 JS 报错）。
- [ ] 文件路径符合 `output_path` 默认或用户指定。
- [ ] 末尾"核查记录"小节如实列出本次人工/工具核查了哪些项。

## 8. 工作约定

- 本 Skill **不调用任何外部 API**，所有内容由当前 AI 基于公开知识生成；资料链接必须经得起点开核查。
- 对概念本身不确定时，**诚实标注"存疑"**，不要硬编。
- 严禁将对话中其他概念的解释"整段搬运"过来凑段落——每个章节都要为本概念定制。
- 与"概念关系说明"配合使用：本 Skill 负责单概念 HTML，关系说明由专门模板承担。
