大模型的上下文 — AI 的"工作记忆"

1. 学习目标

读完这份资料，你应该能：

  • 理解：区分"输入侧 / 输出侧 / 总容量"三层 context window 含义。
  • 理解：解释 Transformer 注意力 O(n²) 复杂度对长上下文的根本性约束。
  • 应用：面对超长文档，能选择合适的策略（全塞 / RAG / 分段摘要）。
  • 区分：说清 context、memory、prompt 三者的边界。
  • 评估：判断"上下文越大越好"这个说法是否成立。

2. 个人解释

我跟人解释"上下文"的时候，最爱用一个比喻：大模型的上下文就像一个人的桌面。桌面越大，你能摊开的资料越多；桌面满了，你只能把最不重要的挪走。

我以前总把"上下文窗口"当成一个简单的"字数限制"，后来发现它其实有三层意思：

  • 输入侧：你这次问问题时能给模型看多少文字（包括历史对话）。
  • 输出侧：模型这次最多能给你写多少字。
  • 总容量：输入 + 输出加起来的 token 上限。

所以我说："上下文 = LLM 一次能'看见'和'产出'的所有 token"。它决定了 LLM 这台机器单次能处理多少信息。

3. 核心问题

读到这里先停一下。围绕"上下文"，这几个问题值得自己先想一遍：

  1. 为什么 Transformer 注意力是 O(n²) 而不是 O(n)？这意味着"上下文翻倍"会带来什么成本？
  2. context window 是不是越大越好？什么是业内所说的 "context rot"？
  3. "扩展窗口"和 "RAG" 是替代关系还是互补关系？分别解决什么问题？
  4. context、memory、prompt 三个概念边界在哪？为什么说"上下文不是越多越安全"？

4. 结构化解释：核心机制与组成

技术细节上，要把握三件事：

  1. Tokenizer 把文本切成 token。英文大约 1 token ≈ 0.75 个单词；中文大约 1 token ≈ 1–2 个汉字。这是计费和窗口的"原子单位"。
  2. 注意力机制是 O(n²) 复杂度。Transformer 的 self-attention 每一层都要让所有 token 互相"看一眼"，所以上下文翻倍，计算量翻四倍。这就是"为什么上下文不能无限长"——不只是显存不够，算力也吃不消。
  3. 长上下文有"有效长度"问题。很多模型号称 200K 上下文，但实际表现只在前 30K 左右好，后面就像"读了但没懂"。业内叫 context rot。

所以要解决长文档问题，工程上不是把上下文做长就完了，主流有三招：

方案核心思路代表
扩展窗口改注意力算法，把 O(n²) 降到 O(n log n) 或更低LongRoPE、YaRN、Mamba
RAG（检索增强）不把所有内容塞给模型，按需检索最相关的几段RAG、向量数据库
摘要/分段长文档先分段，每段总结，最后再总总结Map-Reduce 摘要

5. 应用案例

我最近一次真正"用上"长上下文，是我让 Claude 帮我审一份 90 页的产品需求文档。我没做任何预处理，直接把 PDF 全文贴进去，问它："找出文档里所有前后矛盾的需求点，按章节列出来。"

模型读完反馈说第 3 章说"用户每月最多上传 100 个文件"，第 7 章说"用户每次最多上传 50 个文件"，但需求文档里没明确两者关系。我去核查了一下，确实是个内部矛盾。这种"跨章节的引用一致性"问题，是短上下文模型几乎不可能完成的。

另一个常见但常被低估的场景：代码审查。一次性把整个代码仓库（几千行）丢进去，让模型做架构层面的检查，比只看单个函数有效得多。

6. 概念辨析

  • 上下文 ≠ 记忆（Memory）。上下文是"这一次对话能看见的"，记忆是"跨对话能记住的"。前者由 context window 决定，后者要靠向量库或外部存储。
  • 上下文窗口大 ≠ 表现好。上面说的 "context rot" 就是反例。窗口扩大一倍，价格可能涨四倍，质量提升可能只有 10%。
  • 上下文 ≠ 提示词（Prompt）。提示词只是上下文中"系统指令 + 用户问题"的部分；上下文还包括历史对话、RAG 检索结果、工具返回值等。
  • 边界：上下文不是越多越安全。把无关信息塞进上下文，反而会"分心"（distraction），让模型忽略关键指令。所以"少即是多"在 prompt engineering 里依然是金科玉律。

7. 自测问题

Q1（理解类）context window 的"输入侧 / 输出侧 / 总容量"分别指什么？

答案要点：输入侧 = 这次请求能给模型看多少（用户消息 + 历史 + RAG 片段 + 工具返回）；输出侧 = 模型单次响应最多能生成多少 token；总容量 = 输入侧 + 输出侧的 token 上限。三者经常被混为一谈，是造成"为什么我的回复被截断"误解的根源。

Q2（应用类）给你一份 200 页的 PDF，要让 LLM 回答"作者的核心论点是什么"。你会选：① 全部塞进上下文 ② RAG ③ 分段摘要？说明理由。

答案要点：通常选 ② 或 ③。① 直接塞会超窗（200 页 ≈ 80–150K tokens，多数模型装不下）+ context rot（后段质量衰减）。② RAG：先按段落切、向量化、检索 top-k 段落 + 问题，精确可追溯。③ 分段摘要：每段先总结，再对总结再总结，适合"总论点"类问题。一般"② 优先，③ 兜底"。

Q3（辨析类）"上下文 = 记忆"这个说法对吗？为什么？

答案要点：不对。上下文是当前对话窗口里"可见"的 token，受 context window 约束；记忆是跨会话/跨时间"持久"的，需借助向量库、KV 数据库、外部文件系统等。两者技术实现完全独立：会话结束上下文就消失，但记忆可以保留到下次。

Q4（边界类）为什么说"上下文不是越多越安全"？

答案要点：因为多余内容会产生 distraction（分心），稀释关键指令的权重；同时增加 token 费用、放大 context rot、可能让敏感信息泄漏到上下文。原则是"只放必要信息"。
