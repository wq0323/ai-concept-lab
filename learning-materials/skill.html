Skill — 把"会做的事"封装成可调用的资产

生成于 2026-09-06 · Skill concept-explainer v1.1 · level=intermediate · angle=工程实践

1. 学习目标

读完这份资料，你应该能：

  • 理解：用一句话讲清楚 Skill 的核心定位（"任务知识包"），并说出它与 Prompt 的本质区别。
  • 应用：列出 Skill 的三部分组成（元数据 / 正文指令 / 附加资源）及其各自作用。
  • 区分：说清 Skill、Prompt、Tool、Plugin 四个相邻概念的边界。
  • 设计：为一个具体任务（比如"统一 PR 描述格式"）写出一个 Skill 的 description 草案。

2. 个人解释

我最早接触"Skill"这个词，是在做 AI 助手的时候。我跟同事抱怨："每次让 AI 帮我写 commit message，要么太啰嗦，要么格式不对，每次还得我自己写 prompt。"同事丢给我一个 commit-message Skill，说"你以后调用它就行"。我点了调用，AI 输出的格式突然变得稳定一致——那一刻我才明白：

Skill 是把"一类任务的最佳实践"封装成 AI 能按需加载的资产。

把它想成给 AI 的"工作手册"。每次 AI 接到活儿，先看看有没有对应的 Skill 手册可参考，照着手册干，而不是凭"通才"能力瞎猜。

3. 核心问题

读到这里先停一下。围绕 Skill，这几个问题值得自己先想一遍：

  1. 为什么 Skill 不只是"一段 prompt"？两者的本质区别是什么？
  2. Skill 的 description 字段为什么被设计成"入口"？它和正文的关系是什么？
  3. "万能 Skill" 为什么是反模式？Skill 的颗粒度应该怎么设计？
  4. Skill 和 Tool 各自管什么？它们是替代还是互补？

4. 结构化解释：核心机制与组成

一个标准 Skill 通常由三部分组成：

  1. 元数据（Metadata）：一段 YAML frontmatter，写明 name、description、适用场景。这是 AI 用来判断"这个任务该不该加载这个 Skill"的关键。
  2. 正文指令（Instructions）：Markdown 主体，告诉 AI "加载后应该怎么做"——输入参数、生成步骤、输出结构、自检清单。
  3. 附加资源（References / Assets）（可选）：模板、示例、参考链接、脚本等。Skill 可以挂"工具集"，让 AI 加载 Skill 的同时获得额外能力。

工作流上分两层：

用户发起任务 → AI 看到任务描述
            ↓
    扫描可用 Skill 的 description
            ↓
   匹配？ → 加载 SKILL.md 正文 + 附加资源
            ↓
   按 Skill 的步骤生成结果
            ↓
   按 Skill 的自检清单校验
            ↓
        输出

这套机制的关键设计是：Skill 的 description 是入口，主体是规则。description 决定了"何时触发"，主体决定了"如何执行"。两者都重要，缺一不可。

5. 应用案例

我自己目前在用、且收益最大的场景是"代码审查 Skill"。我写了一份 code-review Skill，要求 AI 在审查 Pull Request 时：

  • 先列变更范围（改了哪些文件、加了多少行）。
  • 按"正确性 / 可读性 / 性能 / 安全性"四类问题分类列出。
  • 每条问题给出严重程度（blocking / suggestion / nit）和具体改法。
  • 末尾给出"通过 / 需修改 / 拒绝"的明确结论。

用了这个 Skill 之后，AI 输出的 review 风格跟团队约定高度一致，不再是"AI 每次风格都不一样"。这才是 Skill 真正的价值——把团队隐性约定变成 AI 的硬约束。

6. 概念辨析

  • Skill ≠ Prompt。Prompt 是一次性的指令，Skill 是结构化的、可复用的资产。一个 Skill 里通常包含 prompt，但远不止 prompt。
  • Skill ≠ Tool / MCP。Tool（工具）是 AI 能调用的外部能力（搜索、发邮件、执行命令）；Skill 是 AI 加载的知识与流程。两者互补，不是替代。
  • Skill ≠ Plugin / 插件。Plugin 通常需要平台支持、注册审核；Skill 是文件级别的资产，开发者自己写、自己管。
  • "万能 Skill"是反模式。一个 Skill 想覆盖所有任务，结果就是什么都不擅长。Skill 的颗粒度应该跟"一类可复用任务"对齐。
  • 边界：Skill 不替你做判断。Skill 提供规范，但最终决策权和责任还在调用者。Skill 写"建议 blocking"，不代表人可以不看。

7. 自测问题

Q1（理解类）一个标准 Skill 由哪三部分组成？分别起什么作用？

答案要点：(1) 元数据（YAML frontmatter）：决定 Skill 在何时被"发现/触发"；(2) 正文指令（Markdown 主体）：决定 Skill 被加载后 AI 该"怎么执行"；(3) 附加资源（可选）：模板/示例/脚本，扩展 Skill 的可执行能力。三者缺一不可——没有元数据不会被发现，没有正文无法执行，没有附加资源则能力受限。

Q2（应用类）如果你们团队想"让 AI 生成的 PR 描述统一格式"，请设计一个 Skill 的 description 字段。

答案要点：description 应说明三件事——什么场景触发、要解决什么问题、加载后会做什么。范例：
"当用户请求为一个 Pull Request 撰写描述时加载。按团队的固定模板（背景 / 改动 / 测试 / 影响范围）输出结构化 Markdown，禁止自由发挥。"
关键是：触发条件明确 + 行为承诺具体，不要写成"帮你写 PR 描述"这种含糊描述。

Q3（辨析类）Skill 和 Tool 的边界在哪？给一个具体例子说明两者如何配合。

答案要点：Skill 管"怎么做"（流程/规范），Tool 管"能做什么"（外部能力）。例子：写一个"竞品分析" Skill，它的工作流是"先列维度 → 检索每家 → 整理表格 → 输出结论"。Skill 本身不提供检索能力，但可以声明需要 web_search 这个 Tool——加载 Skill 后 AI 会自动使用 Tool 完成检索步骤。Skill 提供规则，Tool 提供能力。

Q4（边界类）为什么说"万能 Skill"是反模式？颗粒度应该怎么设计？

答案要点：万能 Skill 想覆盖所有任务，结果是任何任务都做不精——它的 description 模糊、触发不精确、正文指令互相矛盾。正确颗粒度是"一类可复用任务"（如：PR 描述、commit message、SQL 评审、Tailwind 转 CSS）。判断标准：能否用一两句话清晰说明它的触发条件与产出格式；如不能，应拆分。
